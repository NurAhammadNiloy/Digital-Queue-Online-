# MVP manager analytics

`/manager/analytics` uses one selected `locationId` plus `range=today|7days|month|all` (today by default). The page selector lists only the manager's organization; an omitted selection chooses its first location and displays that selection. With no locations, setup guidance replaces all metrics. `GET /api/manager/analytics` requires an explicit `locationId`; missing/invalid/duplicate selectors return 400 and unknown/foreign locations return 404. There is no all-locations mode. Filters use a server-rendered GET form; no raw customer history reaches the browser.

The location-scoped dashboard RPC supplies **served today** and **waiting now**, independent of the history filter. Filtered served count, averages and tables use `get_manager_analytics(text,uuid,text)`. Both RPCs independently validate the manager session and selected location's organization and filter tickets in SQL by organization AND location. The former organization-wide signatures were dropped. Only `service_role` can execute these RPCs; private helpers cannot be executed by browser roles. RLS, session behavior and queue operations are unchanged.

## Definitions

- Only **COMPLETED** tickets participate in filtered served counts and averages. WAITING, SERVING, SKIPPED and CANCELLED tickets are excluded from these metrics.
- Waiting seconds = `started_at - joined_at`; service seconds = `completed_at - started_at`. Existing database constraints require valid ordered timestamps for completed tickets. No duplicate analytics data is stored.
- Membership in a date range uses **completed_at**, not queue_date or joined_at. The selected location's IANA timezone defines calendar boundaries. Today starts at local midnight; last 7 days starts at midnight six calendar days ago; this month starts at local month start. All ranges include their start and end at the RPC's database timestamp, excluding future timestamps. The private helper converts local calendar boundaries to timestamptz, preserving DST behavior.
- Location averages are weighted by individual tickets, not averages of service/staff averages. Service rows contain only services at this location. Staff rows come from matching completed tickets attributed to `served_by_staff_id` at this location, regardless of current assignments. Staff without matching completed history do not appear; staff from another location do not leak into zero-count rows.
- Inactive services, locations and staff retain their historical results. Services with no matching completions show count 0 and null averages, displayed as a dash. An empty location shows zero counts, null averages and clear empty tables. Valid zero durations display as 0 seconds. Precision is retained in JSON; display rounds to the nearest second.
- Filtered summary and both tables share one database snapshot. Live cards reuse the existing dashboard query and may advance independently during concurrent queue actions. Reload/apply the form to refresh; there is no polling.

## Verification

After local migrations and a production build, run `npm run test:analytics`. Isolated real-DB/Auth/HTTP fixtures exercise all four filters, timezone/DST/leap/month boundaries, completion-date membership, weighted averages, incomplete/future exclusions, empty data, inactive history, tenant isolation, session/role guards, RPC grants and rendered pages. Tests remove their fixtures. Interactive browser verification is separate.

Chart series are aggregated in the same location-authorized `get_manager_analytics` snapshot as existing filtered totals. Today uses elapsed-hour buckets anchored to local midnight (repeated DST hours stay separate); Last 7 days/This month use local calendar days. All time uses calendar months from the first completed ticket through the current month. Empty buckets are zero-filled and current buckets are partial; no raw tickets or customer data are returned. The dependency-free line chart includes an expandable exact-count table with timezone offsets for hourly entries. The service bar chart reuses existing served counts. Neither chart subscribes to realtime.

## Clear completed history

The selected location's Analytics page offers a native modal confirmation requiring the current manager password. This removes ALL completed tickets for that location, regardless of the visible date filter. Deleted private ticket links become unavailable and existing foreign-key cascades remove their retry records. Waiting, serving and skipped tickets, configuration and daily numbering counters are untouched. Derived served counts/averages/charts reflect the deletion; ETA history naturally falls back to configured service durations when insufficient samples remain.

`DELETE /api/manager/locations/[id]/analytics/history` accepts only `{password}`. It checks Origin, the manager cookie and location ownership, then obtains the manager's current email from their Auth user ID (never client input). Existing account/IP throttling protects password verification. Supabase Auth verifies the password on the server using a non-persistent client; its temporary session is signed out before deletion. Passwords/tokens are not logged, persisted or returned. The service-role-only `clear_manager_location_history` RPC independently locks/revalidates manager identity, membership, session and location and binds them to the freshly verified Auth user ID. Password changes/session revocation before the transaction invalidate the operation. The delete and dependency cleanup commit or roll back together.

Clearing history does not reset numbers. The unchanged `create_queue_ticket` transaction derives `queue_date` from `clock_timestamp()` in the location IANA timezone, then atomically upserts `(service_id, queue_date)`: a new local day starts at 1. Failed joins roll back ticket and counter together; concurrent joins serialize on the unique counter key. No scheduled task, counter deletion or prefix rewrite is used.
