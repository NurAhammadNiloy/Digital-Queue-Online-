# Manager core administration

Protected pages and APIs reuse the existing manager session guards. Explicit organization filters scope reads. Configuration writes and dashboard counts use service-role-only RPCs that validate and lock manager identity and session, derive organization internally, and verify target ownership. Existing RLS and staff provisioning remain unchanged. No privileged credentials enter client components.

Location slugs are globally unique because `/q/[slug]` has no organization segment. Server-generated slugs have a normalized name plus 64 random bits, with database uniqueness and bounded collision retries. Renaming preserves public URLs and printed QR codes. Location forms accept an IANA timezone, validated server-side and by a database trigger against PostgreSQL's IANA catalog. New locations default to UTC; omitted timezone on an update preserves the existing value. Existing ticket timestamps and numbering are never rewritten.

Dashboard counts belong to one selected location, including that location's inactive configuration/history. The selector contains organization-owned locations with no all-locations option. A missing page selection visibly defaults to the first owned location; an organization without locations gets setup guidance instead of totals. `GET /api/manager/dashboard?locationId=<uuid>` requires a location and returns only waitingNow, currentlyServing and servedToday. The RPC independently checks manager membership and location ownership. Served today uses completion time from local midnight through now in the selected location's IANA timezone. Filtered history lives separately in [MVP analytics](../analytics/README.md).

Operational dashboard counts refresh through [Realtime invalidations](../realtime/README.md) scoped to the selected location, with ten-second polling while visible as fallback. Changing location closes the old subscription and cancels its pending read. Analytics history remains separate and has no subscription.

Location/service updates are atomic and preserve tickets. Existing queue/session validation immediately observes active status and permissions; inactive configuration cannot accept joins or staff actions. Service prefix changes affect new tickets; existing tickets retain their saved prefix.

The single QR dependency, `qr`, runs server-side. SVG codes encode only the configured `APP_ORIGIN` and stable public location slug. QR responses are authenticated, scoped, uncached and downloadable. Print uses the browser's print dialog. No host header or client-provided URL is trusted.

Run `npm run test:manager` against the local Supabase stack after applying migrations and building the app. Tests use isolated fixtures and production HTTP/rendered pages; interactive browser/physical QR scanning is a separate acceptance check.

Location details now use separate, confirmed Activate/Deactivate controls (`PATCH /api/manager/locations/[id]` with an action). Details-only updates omit active and preserve it atomically, avoiding stale form reactivation. `DELETE` with `{}` uses the same manager/session-bound configuration RPC, locks the location, and rejects all service/assignment/ticket/counter dependencies with HTTP 409. Existing FK restrictions remain intact; nothing cascades or removes history. Deactivation blocks even COMPLETE/SKIP until reactivation, as required by existing staff permissions.
